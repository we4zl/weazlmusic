# WeazlMusic listening and pod handoff review

**23 November 2026.** The pod belongs in WeazlMusic. Taking your own queue, position, albums, and radio recordings out the door is exactly the job this software should do. The first thing I would fix is who gets to speak for the listener. I watched an untouched browser tab put an old track back on the dock after the listening tab had selected a new one. The firmware would have received a valid answer containing the wrong track.

The largest measured idle cost came from remote-player discovery. A signed-in listener with no receiver and no pod received 64 identical empty player lists in 16 seconds. The same tab made three pod-status requests. These have different causes and can be fixed independently.

## 1. An untouched tab can overwrite the pod bookmark

**Fix first. Reproduced with Chromium and the actual dock queue handler.** Two tabs on the same origin share the device ID in local storage. Following a browser consequently authorizes both tabs. Each tab has its own remembered last submission. A freshly opened tab can publish its restored track before the user has played anything in it. The server accepts that write and the dock prefers it over the ordinary saved browser queue. [Browser identity](../web/device.js#L2) · [Checkpoint publisher](../web/pod-status.js#L97) · [Dock read and checkpoint write](../internal/server/portable_dock.go#L99)

| Action in the fixture | What the dock returned |
|---|---|
| Select track A in the followed browser and pause it. | A |
| Open a second tab in the same profile. It restores A. Leave it untouched. | A |
| Select track B in the first tab, pause it, and publish the new checkpoint. | B |
| Leave both tabs alone. The second tab submits A and receives HTTP 204. | A after seven seconds, still A another 5.5 seconds later |

The paused first tab had already recorded B as sent. Its duplicate suppression gave it no reason to repair the overwrite. The browser can make a similar mistake after reload because the general queue and the more recent pod checkpoint are stored separately. The two-tab case above is the one I reproduced. [General queue restore](../internal/server/store.go#L168) · [Bookmark selection](../web/player.js#L11)

**Change.** Keep the stable browser identity for pairing. Give the current playback session a separate writer identity and a server-checked generation. Restoring or viewing a queue should never claim the writer role. Transfer ownership on an explicit playback or takeover action. Reject writes from the previous generation, including ones delayed in transit. Include a visible **Stop following** action that keeps the last good bookmark. The current UI hides Follow once selected and the source API only assigns a browser. [Follow control](../web/pod-status.js#L58) · [Source assignment](../internal/server/portable_dock.go#L47)

**Pass condition.** Repeat the table above, then try a reload, a delayed write from the old tab, and an explicit takeover. Check the track occurrence as well as its ID by putting the same song in the queue twice. Opening a tab must leave the dock unchanged. After takeover, only the new writer can move it.

## 2. Remote playback sends four empty snapshots a second to a listener playing locally

**High priority. Measured independently of the new pod work.** After login, the browser opens the remote-player event stream even when there are no receivers. Each connection has a 250 ms server ticker. It collects player state, serializes it, increments the event version, writes a snapshot, and flushes. An unchanged empty list takes this path. A separate 500 ms browser timer checks whether the signed-in user changed. Hiding the tab leaves the remote stream connected. [Browser subscription](../web/remote.js#L103) · [Server ticker](../internal/server/remote_events.go#L63) · [Snapshot write](../internal/server/remote_events.go#L109)

In one 16-second foreground sample on the home screen, Chromium received **64 SSE messages, all containing `[]`**. At that cadence one connected tab gets about **14,400 empty messages per hour**. These are messages on one HTTP connection. The four-per-second cadence is separate from the five-second pod polling below. I measured message counts only.

**Change.** Send the initial inventory, then publish actual changes in receiver availability, transport, queue, commands, or ownership. Use an expiry deadline for a receiver going offline and a sparse connection keepalive if the deployment needs one. Drive subscription lifetime from login and logout. Keep receiver command acknowledgements and active remote playback responsive.

**Pass condition.** With no receiver, a minute after the initial inventory produces zero additional inventory snapshots. Connecting a receiver makes it appear promptly, losing it changes its availability once, and remote play, pause, seek, handoff, and lost-ack recovery still pass the existing browser suite. [Remote integration test](../tests/remote.cjs)

## 3. Every signed-in desk pays for pod discovery

**Confirmed in the same Chromium sample.** Loading any account starts two five-second browser intervals. The first fetches pod status regardless of the current view or pairing. The second considers publishing a checkpoint. An unpaired listener in my 16-second sample made **three status GETs and zero checkpoint PUTs**. At the configured visible cadence that is **720 status reads per hour per tab**, plus the initial fetch, assuming timely responses. A hidden tab skips the status fetch. Sign-out clears the timers. A followed browser can still checkpoint while hidden, which is useful when music continues in the background. [Account startup](../web/auth.js#L11) · [Polling, visibility, and cleanup](../web/pod-status.js#L72)

The unpaired GET reads the account's pack record. For the paired household the same GET also reads the source and schedule and attempts to open three recording or dock JSON files. The in-progress quick actions add **Send to We4zlP0d** to ordinary song, album, and playlist menus even for an unpaired user. Clicking an album or playlist can fetch its contents before the server rejects the send for lack of pairing. [Status handler](../internal/server/portable_status.go#L52) · [Quick actions](../web/quick-actions.js#L58) · [Pairing check](../internal/server/portable_send.go#L37)

**Change.** Supply the pairing capability with existing account state or discover it once. Keep the pod page discoverable, including manual export. Expose automatic Send to accounts that can use it. Subscribe to dock changes for a paired account and refresh when opening the panel or reconnecting. A bounded fallback poll during a visible active transfer is reasonable. Preserve background checkpointing for the actual listening source.

**Pass condition.** An unpaired account left on Home or Albums makes zero recurring pod requests. A newly paired account gains the working actions without a restart. A paired listener can hide the tab, keep listening, and later unplug with a current bookmark. Closing the pod panel during a copy must let the transfer finish.

## 4. A moving playhead resends and stores the whole queue

**Confirmed in source.** The followed browser builds a body containing the current item and every upcoming library track, then stringifies it to detect a change. A one-second position difference changes the string. During advancing playback, each five-second tick can therefore upload the entire queue. The server validates every entry, encrypts the state and upserts the checkpoint. At a full 1,000 upcoming tracks, that cadence can transmit **720,000 upcoming-track entries per hour** from one continuously playing tab. That is an extrapolation from the code. An unchanged paused bookmark suppresses network writes, although the browser still assembles and compares it. The checkpoint route already bypasses the general mutation replay journal. [Payload and comparison](../web/pod-status.js#L97) · [Validation and persistence](../internal/server/portable_dock.go#L151) · [Route](../internal/server/v1_http.go#L129) · [Encrypted upsert](../internal/server/v1_store.go#L145)

The failure mode matters more than the bandwidth. A failed checkpoint is silently retried on the next tick. A permanently rejected queue, for example one over the server's 1,000-upcoming limit, can keep retrying while the dock serves an older valid checkpoint. The existing “Last verified queue” receipt is useful. It describes the card's past state and cannot establish that the latest desktop bookmark reached the server. [Checkpoint limit](../internal/server/portable_dock.go#L158) · [Card receipt display](../web/pod-status.js#L60)

**Change.** Send the ordered track occurrences once per queue revision. Send a small cursor update containing writer generation, queue revision, occurrence ID, and position on seek, pause, track change, and at a bounded interval during playback. Retain the latest acknowledged revision. Back off on transient failures and show a single actionable stale-bookmark indication for a permanent failure. Recorded radio and live radio should retain the held library bookmark where applicable.

**Pass condition.** Play the same track against 10-entry and 1,000-entry queues. Position-only traffic should be about the same size. Seek while hidden, pause, disconnect, reconnect, and reorder duplicate tracks. On recovery the card gets the correct occurrence and position. A rejected update must never imply successful sync.

## 5. The workstation keeps checking after the pod goes home

**Companion finding.** When enabled, the music systemd timer launches a Python process eight seconds after the previous run finishes. The first step invokes `lsblk` to discover a mounted card. An absent card returns before the music worker contacts the server. Separately, the overnight timer starts a process about a minute after each pass. With no card, its normal waiting, ejected, or control-only report goes over SSH and invokes a container command to replace the dock-status file. This explains how a listening desk can display “waiting” indefinitely at a cost even with the player in someone's pocket. These are configured behaviors. I did not sample the running workstation. [Music timer](/home/bobp/hardware/We4zlP0d_Firmware/companion/systemd/we4zlp0d-music.timer) · [Mount discovery and status delivery](/home/bobp/hardware/We4zlP0d_Firmware/companion/overnight_sync.py#L45) · [Absent-card branch](/home/bobp/hardware/We4zlP0d_Firmware/companion/overnight_sync.py#L152)

**Change.** Use attachment and mount transitions to start or stop sync. Publish detach, safe eject, and control-only mode once per transition. Give the server a way to distinguish an unavailable reporting workstation from one that observed an actual detach. Preserve scheduled overnight recording on the server while the card is away. While a writable card is docked, a change in the queue, sends, or published radio edition should wake the copier. Preserve the card lock, mount-identity check, and safe-eject behavior. [Mount and lock checks](/home/bobp/hardware/We4zlP0d_Firmware/companion/desktop_sync.py#L308)

**Pass condition.** Over ten minutes undocked and after a safe eject, count zero recurring music-worker launches, `lsblk` invocations attributable to those workers, or unchanged-status SSH reports. Attach in H2 control-only mode, switch to writable storage, and eject during a copy. Confirm the listener gets each real transition once. Measure power separately before attaching a battery-life claim.

## 6. Sending one item can trigger a library-wide job with no individual recovery control

**In-progress Send path.** The server keeps a durable list of explicit sends. The companion folds pending sends into a single pack, and any pending send forces the rebuild path. That path pages through the track catalog, constructs metadata and discovery shelves, then indexes the card. The server builds and sorts the track list before returning the first page. Later pages reuse its snapshot. Cached media and the five-download concurrency cap help, but sending one song can still require work proportional to the library. [Pending-send test in the companion](/home/bobp/hardware/We4zlP0d_Firmware/companion/desktop_sync.py#L213) · [Pack catalog scan](/home/bobp/hardware/We4zlP0d_Firmware/companion/sync.py#L743) · [Server pagination](../internal/server/v1_library_routes.go#L96)

Explicitly sent tracks join the required set. A removed upstream track without a usable local copy, or a required item that cannot fit, can abort the pack. The dock acknowledges the batch after a successful pass. The browser offers a queued toast, with no list of outstanding selections or way to withdraw the item holding things up. This is a source-traced failure path. I did not simulate a full SD card. The existing receipt design is worth keeping. Its test proves that a late confirmation for an older send leaves a newer send for the same playlist pending. [Required tracks and download failure handling](/home/bobp/hardware/We4zlP0d_Firmware/companion/sync.py#L772) · [Acknowledgement](/home/bobp/hardware/We4zlP0d_Firmware/companion/desktop_sync.py#L299) · [Receipt regression test](../internal/server/portable_send_test.go#L40)

**Change.** Keep the last playable index during a failed transfer. Expose pending, verified, blocked, retry, and cancel per selection on the pod page. Let independent healthy sends complete while retaining failed selections with a specific reason. Reuse a known catalog revision for unrelated sends. A full card-index rewrite may be required by the firmware format. Measure that cost separately from a fresh server catalog scan and optional artwork or discovery work.

**Pass condition.** Queue two albums, remove an uncached track from one, and dock. The complete album should be available, the incomplete one should name the blocking track, and cancelling it should let subsequent transfers proceed. Repeat with low space and an interrupted transfer. For a single-song addition to an unchanged large library, record catalog requests, card bytes read and written, and time until safe eject.

## 7. Music-only pairing and the return trip assume one installation layout

**Two distinct portability issues.** The dock socket starts only when `NIGHTLY_POD_SOURCE_JOB` is configured. The browser's pairing and send checks identify the dock by the overnight radio schedule's account and library. On a fresh music-only installation, following a queue therefore depends on first configuring a recorder job. The initial schedule also uses a fixed New York time window. This is understandable on the original household node. It is avoidable setup for someone who just wants their albums in their pocket. [Startup gate](../internal/server/v1_store.go#L101) · [Initial schedule](../internal/server/recorder_nightly.go#L75) · [Send eligibility](../internal/server/portable_send.go#L37)

The automatic companion also puts a fixed LAN origin into the trip. The return helper preserves that origin, and the web importer requires an exact match with the currently open site's origin. A person who used the same installation through its HTTPS reverse proxy can be told their own return file belongs to another server. Conversely, the origin alone cannot distinguish two accounts or libraries behind that address. The card cache already uses account and library identity, and the API exposes an installation ID. Those are useful building blocks for a versioned transfer format. [Companion origin and generated trip](/home/bobp/hardware/We4zlP0d_Firmware/companion/desktop_sync.py#L275) · [Return-file writer](/home/bobp/hardware/We4zlP0d_Firmware/companion/sync.py#L445) · [Browser validation](../web/we4zlp0d.js#L87) · [Installation ID](../internal/server/v1_http.go#L124)

**Change and pass condition.** Give the dock its own account and library binding. Test queue sync on a fresh node with radio capture disabled. For new trip files, bind the return to installation, account, and library. Keep a deliberate compatibility path for existing files. Test LAN-to-HTTPS return on the same installation and a same-host different-library return. The first should resume the selected occurrence. The second should leave the current queue intact.

## What I would ship first

1. **Land the writer fix and the two-tab regression test before changing firmware resume logic.** The dock already returned the wrong track before USB or firmware entered the picture.
2. **Remove the measured empty remote stream traffic and unpaired pod polls.** Keep automatic discovery, real playback in hidden tabs, and visible transfer progress. They are valuable.
3. **Separate queue revisions from position, then give pending sends a recovery path.** This makes both “Continue” and “Queued” promises the listener can verify.
4. **Bench-test real dock transitions and interruption boundaries.** The pack publishes the compact index, covers, library database, resume record, and trip metadata across multiple writes. Exercise ejection or loss of power between those publications on a sacrificial card. Check the last playable edition, the duplicate-track occurrence, the bookmark, and the delivery receipt after remount. Individual atomic file replacements alone do not establish what the player sees across that whole sequence. [Card publication sequence](/home/bobp/hardware/We4zlP0d_Firmware/companion/sync.py#L897)

## Review basis and verification

The review used the local WeazlMusic working tree captured at 21:25 EST, based on `605926e66cf4`, including the uncommitted Send, receipt, eject-status, and browser changes. Companion sources came from the active firmware working tree based on `29f317231ad7`. File references identify the reviewed functions and may move as development continues.

The isolated music snapshot passed `go test -race ./...`, the browser smoke and remote-receiver suites, and the dedicated pod export/return Chromium test. The handoff experiment used a separate copy of the fixture with the synthetic account assigned a dock and its real Unix socket enabled. It exercised the normal browser checkpoint endpoint and read the resulting dock queue. The unpaired idle experiment used the stock fixture and Chromium network events. A clean test run and the reproduced handoff failure are compatible because the existing pod browser test exercises export, duplicate tracks, return, and cancel in one tab. [Pod browser coverage](../tests/we4zlp0d.cjs) · [Dock handler coverage](../internal/server/portable_status_test.go#L44)

These findings cover the listener, browser, server, and companion boundary. USB behavior, flash wear, watts, and physical interruption recovery still need measurements on the target hardware. The runtime evidence here ends at the dock socket.
